# Escenarios de amenazas STRIDE: `GET /api/v1/products/{id}`



## 1. Escenario: Suplantación de identidad (S - Spoofing)

**Tipo de amenaza:** Spoofing.

**Escenario:** Peticiones falsificadas pasando por alto el Gateway si el microservicio escucha en IP pública.

**Riesgo:**
- Peticiones falsificadas pasando por alto el Gateway si el microservicio escucha en IP pública.

**Mitigación:**
- Red privada aislada; el microservicio solo acepta tráfico proveniente del API Gateway.

## 2. Escenario: Manipulación de datos (T - Tampering)

**Tipo de amenaza:** Tampering.

**Escenario:** Un atacante manipula el parámetro `id` de `GET /api/v1/products/{id}` introduciendo caracteres especiales o valores maliciosos para intentar alterar la consulta a la base de datos. Por ejemplo: `GET /api/v1/products/100%27`.

**Riesgo:**
- Posible explotación de inyección SQL si se construyen consultas inseguras.
- Acceso no autorizado a información almacenada.
- Alteración de consultas y, dependiendo de los permisos, posible modificación de información.
- Comportamiento inesperado del servicio.

**Mitigación:**
- Validar que `id` tenga el formato esperado (UUID o Integer).
- Utilizar consultas parametrizadas.
- Evitar concatenar entradas externas en consultas SQL.
- Implementar manejo seguro de excepciones.
- Aplicar mínimo privilegio a la cuenta de base de datos.

## 3. Escenario: Repudio de acciones (R - Repudiation)

**Tipo de amenaza:** Repudiation.

**Escenario:** Un consumidor realiza múltiples consultas a `GET /api/v1/products/{id}`, pero la aplicación no registra adecuadamente las solicitudes, lo que dificulta investigar actividades sospechosas.

**Riesgo:**
- Dificultad para reconstruir eventos durante un incidente.
- Dificultad para identificar patrones de consultas sospechosas.
- Falta de evidencia técnica para investigar abusos del servicio.

**Mitigación:**
- Implementar registros de acceso a la API.
- Registrar fecha, hora, endpoint y código de respuesta HTTP.
- Incorporar identificadores de correlación.
- Centralizar y proteger los logs contra modificaciones no autorizadas.
- Implementar monitoreo y alertas.

**Consideración:** Al ser un endpoint público, los logs permiten rastrear solicitudes, pero no identificar de forma confiable a una persona sin autenticación adicional.

## 4. Escenario: Divulgación de información (I - Information Disclosure)

**Tipo de amenaza:** Information Disclosure.

**Escenario:** Un atacante consulta `GET /api/v1/products/{id}` y recibe campos internos que no deberían exponerse públicamente, como costos de proveedores o notas administrativas.

**Ejemplo hipotético de respuesta con información interna:**

```json
{
  "id": 100,
  "name": "Laptop",
  "price": 15000,
  "supplierCost": 9000,
  "internalNotes": "Proveedor estratégico"
}
```

**Riesgo:**
- Exposición de información comercial confidencial.
- Divulgación de datos internos.
- Uso indebido de información sensible por terceros.
- Posible afectación económica o reputacional.

**Mitigación:**
- Implementar DTOs para controlar los atributos devueltos.
- Exponer únicamente información autorizada para consulta pública.
- Evitar devolver entidades completas de base de datos.
- Configurar correctamente la serialización JSON.
- Evitar mostrar información interna en mensajes de error.

## 5. Escenario: Denegación de servicio (D - Denial of Service)

**Tipo de amenaza:** Denial of Service.

**Escenario:** Un atacante envía un volumen excesivo de solicitudes automatizadas a `GET /api/v1/products/{id}`, consumiendo recursos del servidor y conexiones a la base de datos.

**Riesgo:**
- Saturación de recursos del servidor.
- Incremento en tiempos de respuesta.
- Agotamiento de conexiones a la base de datos.
- Interrupción temporal del servicio.
- Afectación a consumidores legítimos.

**Mitigación:**
- Implementar rate limiting.
- Establecer límites de solicitudes por cliente.
- Configurar timeouts.
- Implementar caché para consultas frecuentes.
- Monitorear consumo de recursos y tráfico anómalo.
- Utilizar protección DDoS cuando corresponda.

## 6. Escenario: Elevación de privilegios (E - Elevation of Privilege)

**Tipo de amenaza:** Elevation of Privilege.

**Escenario:** Un atacante aprovecha una configuración incorrecta de permisos o una falla de aislamiento para conseguir que el endpoint público `GET /api/v1/products/{id}` permita acceder a información o recursos reservados para usuarios privilegiados.

**Riesgo:**
- Acceso no autorizado a recursos administrativos.
- Exposición de información restringida.
- Posible utilización de funciones con privilegios superiores.
- Compromiso de otros componentes del sistema.

**Mitigación:**
- Aplicar el principio de mínimo privilegio.
- Separar endpoints públicos de los administrativos.
- Implementar autorización para operaciones y recursos restringidos.
- Validar que el endpoint solo consulte productos públicos.
- Restringir permisos de la aplicación sobre la base de datos.
- Realizar pruebas de autorización y aislamiento.

**Consideración:** Este escenario es condicional: la información del caso no confirma la existencia de funciones privilegiadas accesibles desde el endpoint.
